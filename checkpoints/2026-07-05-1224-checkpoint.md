## What we did this session
- **Diagnosed NVFP4-slower-than-bf16 (from source, not guessing):** the Phase C
  `nvfp4_w4a16_matmul_cuda` re-materializes the ENTIRE fp4 weight to a bf16 `[N,K]`
  DRAM buffer **every forward pass** (`enqueue_create_buffer`+`enqueue_fp4_materialize`
  then dense GEMM) → ~2.25× the weight DRAM traffic of bf16 + double the kernel
  launches. Fixed per-forward cost ∝ weight size, independent of image size → dominates
  at small M. Measured on klein: ~0.66 s/128² img NVFP4 vs user's ~0.17 s bf16 (~4×).
- **Diagnosed the earlier klein compile-hang** (misattributed by me in a prior session):
  klein (VMID 242) has **8 cores / 32 GB RAM** vs max-build's **16 / 64**; the cold
  graph-compile swap-thrashes (`pswpout`≈89 GB paged out; 5h13m serve, never ready,
  SIGTERM). Files byte-identical to max-build (all 9 sha256 match) → NOT code/wheel; it's
  **RAM starvation**. (The one dmesg OOM was `/lxc/208 whisper`, a different container —
  did NOT misattribute this time.)
- **Built D1 fused kernel** `nvfp4_w4a16_fused_cuda.mojo`: decode packed fp4 weight →
  bf16 **in the GEMM mainloop** (reuse `decode_e2m1_to_f32` + `TensorCore` mma +
  `cp.async`) instead of a full materialize. Then optimized: vectorized SIMD decode →
  cp.async 2-stage pipeline → **split-K** (launcher-internal, op/py unchanged) + single-
  buffer decoded-B. Correct throughout (oracle test `test_linear_nvfp4_cuda_fused_matches_materialize` PASSES on sm_120).
- **D1 result (L2-flushed, realistic bf16):** 3–6× faster than the naive fused baseline;
  **beats the deployed materialize path everywhere at M≤256** (fused/mat 0.19–0.73×, up
  to ~5× faster); but still **2.3–5.7× off bf16** (best 2.30× at M=64). Wall = the
  scalar-ALU fp4→bf16 decode (M-independent, ~29–40 vs bf16 68–89 TFLOP/s). D1 ceiling ≈
  bf16 parity.
- **Fixed the benchmark L2 caveat:** back-to-back timing kept the weight L2-resident →
  bf16 M=1 = 3.6 µs (L2 BW, not DRAM). L2-flushed bench → realistic bf16 M=1 ≈ 13 µs.
- **D2 spike: GO** — native sm_120 FP4 tensor cores work.
  `mma.sync.aligned.m16n8k64.row.col.kind::mxf4nvf4.block_scale.scale_vec::4X.f32.e2m1.e2m1.f32.ue4m3`
  assembles for `sm_120a` via **raw inline PTX** (NOT the `llvm.nvvm.mma.block_scale`
  intrinsic — CUTLASS #3227 shows ptxas rejects that) and is **numerically exact** vs a
  host reference (4 escalating tests). Spike: `nvfp4_mma_spike.mojo`.
- **Discovered native FP4 = FP4×FP4** (no bf16×FP4 MMA), so beating bf16 requires
  **activation quantization** (W4A4/W4A8) — accuracy risk on a weight-only model. User
  chose **W4A4 (max speed)**. Also found the activation *quantizer*
  (`quantize_dynamic_block_scaled`/`fp4_quantization.mojo:2070`) is **SM100-only** on
  sm_120 → D2 needs an sm_120 activation quantizer too.
- **Started the W4A4 accuracy pre-check** (before building the GEMM): fp4-activation
  fake-quant render vs known-good. IN FLIGHT.

## Lessons learned
- **sm_120 ≠ sm_100 tensor cores.** sm_120 (GB202, RTX PRO 6000) uses **warp-level
  `mma.sync`** block-scaled FP4/FP8; sm_100 (B200) uses **tcgen05/UMMA**. In MAX, BOTH
  the block-scaled MMA (`KIND_MXF4NVF4`) AND the block-scaled quantize are **SM100-gated**
  → sm_120 needs its own. TN layout only, cluster 1×1×1, ~2× Ada fp8 rate.
- **Native FP4 tensor cores are FP4×FP4** — no bf16×FP4 path. Beating bf16 forces
  activation quantization (W4A4 = fp4 act, 1 mantissa bit = image-quality risk; W4A8 =
  fp8 act via `mxf8f6f4`, safer).
- **Use RAW inline PTX** for sm_120 block-scale `mma.sync`; the LLVM intrinsic path is
  ptxas-rejected (#3227). Model on the fp8 `mma.sync` at `mma_nvidia.mojo:237`.
- **Benchmark L2 caveat:** timing the same kernel back-to-back keeps the weight
  L2-resident → an unrealistically fast bf16 bar. Always L2-flush for quant-vs-bf16.
- **D1 (materialize→in-mainloop decode) ceiling ≈ bf16 parity** — after decode it's the
  same bf16 MMA; the decode is pure overhead. Only D2 (FP4 tensor cores: hardware decode
  + 2× throughput) can clearly beat bf16.
- **Split-K is the small-M occupancy lever** (few output blocks at small M → underfilled
  GPU); larger BK hurt (occupancy drop); 3-stage pipeline was neutral (decode-bound).
- **De-risk the linchpin with a minimal spike before committing weeks** — proving one
  FP4 MMA (assembles + numerically correct) retired the biggest D2 risk in ~18 min. Now
  applying the same to the W4A4 accuracy risk (fake-quant render before the GEMM). User
  endorses this sequencing at every fork.
